3.3 Session Management Patterns
--------------------------------------------------------------------------------

Instance Creation Flow:
1. API call to create new session
2. Generate QR code
3. User scans QR with WhatsApp mobile app
4. Session transitions to "connected" status
5. Store session credentials in database
6. Ready for messaging

Session Storage Options:
- File-based (LocalAuth) - not for ephemeral hosts
- Database (PostgreSQL/MySQL/SQLite)
- Redis (for session state/cache)
- S3/MinIO (for backups)

Reconnection Handling:
- Automatic reconnection logic
- QR refresh on timeout
- Session restoration from stored credentials

4.5 WEBHOOK BEST PRACTICES
--------------------------------------------------------------------------------

Security:
- HMAC signature validation (RFC 2104)
- Constant-time digest comparison
- Payload format validation
- API keys per endpoint
- OAuth 2.0 where needed
- IP allow-listing

Reliability:
- Enqueue events to durable queue
- Return 2xx immediately after persisting
- Exponential backoff + jitter for retries
- Dead Letter Queue (DLQ) for failed events
- Idempotency with message IDs

Performance:
- Quick acknowledgment (< 10 seconds)
- Async processing after ACK
- Fan-out pattern for multiple actions

CRM-Specific:
- Ignore integration user changes
- Compare timestamps
- Use directional flags to prevent loops
- Handle at-least-once delivery

5. WHATSAPP WEB PROTOCOL & REVERSE ENGINEERING
================================================================================

--------------------------------------------------------------------------------
5.1 Protocol Overview
--------------------------------------------------------------------------------

WhatsApp Web uses:
- WebSocket for real-time communication
- Binary protocol (protobuf)
- Signal Protocol for E2E encryption

Encryption:
- AES 256 CBC
- Curve25519 (Diffie-Hellman)
- HKDF for shared secret
- HMAC with SHA256

Multi-Device Architecture:
- Up to 4 devices can send/receive directly
- Each device has E2E encryption with contacts
- Server coordinates message delivery

6. DATABASE SCHEMAS & ARCHITECTURES
================================================================================

--------------------------------------------------------------------------------
6.1 Database Recommendations
--------------------------------------------------------------------------------

| Database   | Use Case                  | Performance              |
|------------|---------------------------|--------------------------|
| PostgreSQL | User profiles, CRM data   | 1-5ms read, 2-10ms write |
| Cassandra  | Messages, time-series     | 1-10ms read, <1ms write  |
| MongoDB    | Messages, flexible schema | Depends on setup         |
| Redis      | Cache, sessions, real-time| <1ms read/write          |

Recommended Pattern:
- PostgreSQL for ACID transactions (contacts, users, settings)
- Cassandra/MongoDB for high-volume messages
- Redis for caching and real-time data

--------------------------------------------------------------------------------
6.2 Core Entities
--------------------------------------------------------------------------------

Users/Contacts:
```sql
CREATE TABLE contacts (
    id UUID PRIMARY KEY,
    tenant_id UUID NOT NULL,
    whatsapp_id VARCHAR(50),
    phone VARCHAR(20),
    name VARCHAR(255),
    email VARCHAR(255),
    avatar_url TEXT,
    metadata JSONB,
    created_at TIMESTAMP DEFAULT NOW(),
    updated_at TIMESTAMP DEFAULT NOW()
);
```

WhatsApp Sessions:
```sql
CREATE TABLE whatsapp_sessions (
    id UUID PRIMARY KEY,
    tenant_id UUID NOT NULL,
    session_name VARCHAR(100),
    phone_number VARCHAR(20),
    status VARCHAR(20), -- connected, disconnected, qr_pending
    qr_code TEXT,
    credentials JSONB,
    last_connected_at TIMESTAMP,
    created_at TIMESTAMP DEFAULT NOW()
);
```

Conversations:
```sql
CREATE TABLE conversations (
    id UUID PRIMARY KEY,
    tenant_id UUID NOT NULL,
    session_id UUID REFERENCES whatsapp_sessions(id),
    contact_id UUID REFERENCES contacts(id),
    last_message_at TIMESTAMP,
    unread_count INTEGER DEFAULT 0,
    status VARCHAR(20), -- open, closed, pending
    assigned_to UUID,
    created_at TIMESTAMP DEFAULT NOW()
);
```

Messages:
```sql
CREATE TABLE messages (
    id UUID PRIMARY KEY,
    conversation_id UUID REFERENCES conversations(id),
    whatsapp_message_id VARCHAR(100),
    direction VARCHAR(10), -- inbound, outbound
    type VARCHAR(20), -- text, image, video, audio, document
    content TEXT,
    media_url TEXT,
    status VARCHAR(20), -- pending, sent, delivered, read, failed
    metadata JSONB,
    created_at TIMESTAMP DEFAULT NOW()
);
```

--------------------------------------------------------------------------------
6.3 Pagination Strategies
--------------------------------------------------------------------------------

Cursor-Based Pagination (Recommended):
- Use message timestamp or sequence number as cursor
- More efficient for real-time chat
- No issues with data changes between pages

Example:
```sql
SELECT * FROM messages
WHERE conversation_id = ?
AND created_at < ?  -- cursor
ORDER BY created_at DESC
LIMIT 50;
```

Sharding Strategy:
- Modulo-based sharding by conversation_id
- conversation_id % 10 = table_number
- Distribute load across multiple tables

--------------------------------------------------------------------------------
6.4 Message Ordering
--------------------------------------------------------------------------------

Server Sequence Numbers:
- Assign sequence on server receipt
- Use as tie-breaker for simultaneous messages
- Clients render by sequence order

Schema Addition:
```sql
ALTER TABLE messages ADD COLUMN sequence_number BIGINT;
CREATE INDEX idx_messages_sequence ON messages(conversation_id, sequence_number);
```

--------------------------------------------------------------------------------
7.3 Redis + BullMQ
--------------------------------------------------------------------------------
GitHub: https://github.com/taskforcesh/bullmq
Documentation: https://docs.bullmq.io

Description:
- Message Queue and batch processing
- Node.js, Python, Elixir, PHP support
- Built on Redis

Key Features:
- Delayed jobs (scheduled messages)
- Repeatable jobs (recurring tasks)
- Rate limiting
- Retries with backoff
- Priority queues
- Job progress tracking

WhatsApp Message Scheduling Example:
```javascript
import { Queue, Worker } from 'bullmq';

const messageQueue = new Queue('whatsapp-messages', {
    connection: { host: 'localhost', port: 6379 }
});

// Schedule a message
await messageQueue.add('send-message', {
    sessionId: 'session-1',
    to: '1234567890@s.whatsapp.net',
    message: 'Hello!'
}, {
    delay: 60000 // Send in 1 minute
});

// Process messages
const worker = new Worker('whatsapp-messages', async (job) => {
    const { sessionId, to, message } = job.data;
    await sendWhatsAppMessage(sessionId, to, message);
});
```

--------------------------------------------------------------------------------
7.4 Recommended Architecture
--------------------------------------------------------------------------------

```
[API Server] --> [Redis/BullMQ] --> [Worker Processes]
                      |
                      v
               [WhatsApp Sessions]
                      |
                      v
               [WhatsApp Servers]
```

Benefits:
- Decoupled message sending
- Retry on failures
- Rate limiting per session
- Scheduled/delayed messages
- High throughput

9. WEBHOOK PATTERNS & REAL-TIME MESSAGING
================================================================================

--------------------------------------------------------------------------------
9.1 WebSocket vs Socket.IO
--------------------------------------------------------------------------------

WebSocket:
- Raw protocol
- Lower latency, higher throughput
- Minimal overhead
- Best for maximum performance

Socket.IO:
- Library over WebSocket
- Auto-reconnection
- Rooms and namespaces
- Fallback to long-polling
- Better for development speed

Recommendation:
- Use Socket.IO for CRM dashboard (ease of development)
- Use WebSocket for high-performance bots

--------------------------------------------------------------------------------
9.2 Real-Time Architecture
--------------------------------------------------------------------------------

```
[WhatsApp API] --> [Webhook Endpoint] --> [Message Queue]
                                               |
                                               v
                                    [Event Processor]
                                               |
                      +------------------------+------------------------+
                      |                        |                        |
                      v                        v                        v
               [Database]            [Socket.IO Server]          [Webhook Delivery]
                                               |
                                               v
                                    [Client Dashboards]
```

--------------------------------------------------------------------------------
9.3 Event Types to Handle
--------------------------------------------------------------------------------

From WhatsApp:
- messages.upsert (new/updated messages)
- messages.update (status changes)
- messages.delete
- contacts.update
- chats.update
- presence.update
- connection.update (session state)
- qr (QR code generated)

To Clients:
- new_message
- message_status_update
- typing_indicator
- session_status
- contact_update

--------------------------------------------------------------------------------
9.4 Webhook Delivery to External Systems
--------------------------------------------------------------------------------

Retry Strategy:
- Exponential backoff: 1s, 2s, 4s, 8s, 16s...
- Max retries: 5-10
- Dead Letter Queue after failures

Payload Format:
```json
{
    "event": "message.received",
    "timestamp": "2026-01-21T10:30:00Z",
    "data": {
        "messageId": "ABC123",
        "from": "1234567890",
        "to": "0987654321",
        "type": "text",
        "content": "Hello!",
        "timestamp": "2026-01-21T10:29:55Z"
    },
    "session": {
        "id": "session-uuid",
```

================================================================================
11. MULTI-TENANT SAAS ARCHITECTURE
================================================================================

--------------------------------------------------------------------------------
11.1 Multi-Tenancy Models
--------------------------------------------------------------------------------

1. Shared Database (Pooled):
   - All tenants share tables
   - TenantID column for isolation
   - Row-Level Security (RLS)
   - Lowest cost, easiest scaling
   - Risk: "noisy neighbor" queries

2. Database per Tenant:
   - Complete data isolation
   - Higher cost
   - Better for compliance

3. Schema per Tenant:
   - Middle ground
   - Shared database, separate schemas

Recommendation for WhatsApp CRM:
- Shared database with tenant_id columns
- PostgreSQL Row-Level Security
- Redis cache per tenant (prefix keys)

--------------------------------------------------------------------------------
11.2 Key Patterns
--------------------------------------------------------------------------------

Tenant Identification:
- Subdomain (tenant1.app.com)
- Request header (X-Tenant-ID)
- JWT claim

Data Isolation:
```sql
-- PostgreSQL RLS
ALTER TABLE messages ENABLE ROW LEVEL SECURITY;

CREATE POLICY tenant_isolation ON messages
    FOR ALL
    USING (tenant_id = current_setting('app.current_tenant')::uuid);
```

WhatsApp Session Isolation:
- Each tenant has own sessions
- Session credentials encrypted per tenant
- Separate webhook endpoints per tenant

--------------------------------------------------------------------------------
11.3 Security Checklist
--------------------------------------------------------------------------------

- Data encryption at rest and in transit
- Role-based access control (RBAC)
- Multi-factor authentication
- Tenant data isolation validation
- API rate limiting per tenant
- Audit logging
- Regular security assessments


================================================================================
12. RISKS & LEGAL CONSIDERATIONS
================================================================================

--------------------------------------------------------------------------------
12.1 Terms of Service Violations
--------------------------------------------------------------------------------

WhatsApp's Position:
- Unofficial apps violate Terms of Service
- No validation of security/privacy practices
- Risk of temporary or permanent bans

Warning Signs Before Ban:
"It looks like you may be using tools that don't follow our terms to
send automated or bulk messages. This will lead to your account being
restricted."

--------------------------------------------------------------------------------
12.2 Tools That Trigger Bans
--------------------------------------------------------------------------------

High Risk:
- GB WhatsApp, FM WhatsApp, WhatsApp Plus
- Unauthorized browser extensions
- Third-party bulk messaging tools
- Chrome extensions
- WhatsApp mods
- Number scraping tools

Lower Risk (but still unofficial):
- Baileys-based APIs (used responsibly)
- whatsapp-web.js implementations
- Evolution API (with proper usage)

--------------------------------------------------------------------------------
12.3 Best Practices to Minimize Risk
--------------------------------------------------------------------------------

1. Number Warm-up:
   - Start with 30-50 messages/day
   - Gradually increase over weeks
   - Don't send bulk immediately

2. Message Quality:
   - No spam or unsolicited messages
   - Personalized content
   - Respect opt-outs

3. Session Management:
   - Don't login from many locations
   - Maintain stable sessions
   - Handle disconnections gracefully

4. Rate Limiting:
   - Respect WhatsApp's unofficial limits
   - ~200-500 messages/day per number (conservative)
   - Delays between messages

--------------------------------------------------------------------------------
12.4 Official Alternative: WhatsApp Business API (WABA)
--------------------------------------------------------------------------------

For Production/Commercial Use:
- Partner with BSPs (Business Solution Providers)
- Meta Tech partners
- 100% policy-compliant
- SLAs and support
- Analytics and compliance features

Cost:
- Per-conversation pricing
- Template message fees
- BSP fees vary

When to Use Official API:
- Business-critical applications
- High message volumes
- Compliance requirements
- Need for support/SLAs

13.4 Quick Start with Evolution API
--------------------------------------------------------------------------------

```yaml
version: '3.8'

services:
  evolution-api:
    image: atendai/evolution-api:latest
    ports:
      - "8080:8080"
    environment:
      - DATABASE_URL=postgresql://user:pass@postgres:5432/evolution
      - REDIS_URL=redis://redis:6379
      - WEBHOOK_URL=http://your-app:3000/webhook
    depends_on:
      - postgres
      - redis

    image: postgres:15
    environment:
      - POSTGRES_USER=user
      - POSTGRES_PASSWORD=pass
      - POSTGRES_DB=evolution
    volumes:
      - postgres_data:/var/lib/postgresql/data

      - redis_data:/data

volumes:
```
